# Rust streamer prototype

**Status:** Capture and software-encoding adapters, bounded RTSP/SDP/TCP session setup, a capture-to-encode-to-UDP pipeline, Moonlight RTP/NV_VIDEO_PACKET data and Reed-Solomon parity shards, a Moonlight video AES-GCM envelope, the isolated PIN-to-AES-key derivation primitive, bounded raw AES-128-ECB pairing blocks, and a four-stage host-side pairing transaction with RSA certificate/key binding and challenge-proof verification, a bounded four-phrase query/XML adapter, an expiring pending-client approval binding, an atomic local pairing identity store that accepts transaction-created client records, applies private Linux permissions, and zeroizes private-key buffers, an incremental 64 KiB-bounded GameStream HTTP/query parser, a coordinator for expiring PIN approvals and per-client pairing transactions, and a validated Moonlight launch-key parser that creates per-session RTSP/video ciphers are implemented. The transaction returns a client record only after both transcript and signature checks succeed. The coordinator keeps pending client material out of the operator summary, binds PIN approval to a random short-lived token, and persists the client only after the final proof succeeds. Pairing query/XML handling, a bounded HTTP parser, approval coordination, and transactional certificate persistence are implemented as library boundaries; TLS pairing confirmation, authenticated HTTP listener integration, approval UI wiring, launch routing, worker listener integration, and real-client compatibility remain incomplete. The pairing store's server key is not encrypted at rest; owner-only local permissions are the current protection.

The `aphelion-streamer` crate accepts an already encoded H.264 access unit as separate NAL units, packetizes single NALs and large NALs (FU-A), assigns RTP sequence/timestamp/SSRC fields, and sends the resulting datagrams to a configured UDP destination. RTP packetization follows the general RTP header and H.264 payload conventions in [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550.html) and [RFC 6184](https://www.rfc-editor.org/rfc/rfc6184.html). The caller supplies a 90 kHz media timestamp; the crate does not infer media timing.

`PipeWireCapture` reads fixed-size BGRA frames from a caller-selected PipeWire node through GStreamer and places a two-buffer downstream-leaky queue before raw frame delivery, so overload favors recent frames. The Rust timestamp is when a complete frame arrives over the process pipe; the underlying PipeWire timestamp is currently lost. The node must come from an authorized desktop portal session; this crate does not request permission or enumerate displays. `FfmpegH264Encoder` feeds those frames to a separate FFmpeg `libx264` process and parses Annex-B access units using AUD boundaries. The encoder uses a bounded two-unit output channel and keeps monotonic frame-receipt timestamps. GStreamer timestamp metadata is not preserved over the raw pipe, so current latency measurements start when a complete frame reaches the Rust process. These are synchronous media-thread adapters, not yet connected to the supervisor worker lifecycle or user-facing display chooser. FFmpeg/GStreamer binaries and codec plugins are runtime dependencies and are not bundled.

The bounded RTSP decoder now feeds a conservative session state machine with ANNOUNCE, SETUP, PLAY, GET_PARAMETER, and TEARDOWN ordering, CSeq correlation, exact duplicate replay, and duplicate-conflict rejection. `serve_rtsp_connection` adapts one accepted TCP connection to that decoder and state machine, handles fragmented and pipelined requests, writes ordered responses, reports lifecycle events after response writes, reports a clean RTSP-control disconnect after a session has begun, and detects disconnects mid-message. The embedding worker owns listener policy, finite socket timeouts, and authentication. `serve_encrypted_rtsp_connection` authenticates each bounded record before parsing, rejects cleartext on that path, seals ordered responses, and reports clean disconnects; it requires a key already established by authenticated launch negotiation. ANNOUNCE SDP has bounded parsing for viewport size, frame rate, packet size, bitrate, codec, FEC minimum, and selected feature/encryption flags; the resulting profile is exposed on the session. Invalid, duplicate, missing, or out-of-range recognized fields reject ANNOUNCE without advancing lifecycle state. Unknown fields are ignored for forward compatibility. SETUP validates unicast RTP/RTCP client port pairs and returns the server pair only when the caller constructed the session with ports already reserved by media sockets. It can also resolve the client RTP/RTCP endpoints using the accepted RTSP peer IP and negotiated ports; the session does not trust an address supplied by SDP. `ReservedUdpPortPair` now reserves an OS-selected even RTP port plus its consecutive RTCP port, and `MoonlightUdpSender::bind_reserved` sends from that exact RTP port while keeping RTCP reserved. Audio/control socket ownership is still incomplete. `MoonlightPairingKey::from_pin` validates four ASCII digits and derives the 128-bit pairing key from the 16-byte salt plus PIN using SHA-256, then zeroizes its key bytes on drop. `MoonlightPairingTransaction` implements the four host-side cryptographic phases, binds the server certificate to its RSA private key and the PIN approval to one pending client identity/certificate, enforces phase order, verifies both challenge transcripts and the client's RSA signature, and returns a client record only after success. Exact final-request retries replay the same paired result; conflicting retries are rejected. The pairing transaction is now exposed through a bounded query/XML adapter, but the live host still does not authenticate clients: HTTPS listener/TLS confirmation, operator-facing approval UI connected to the expiring request object, durable authorization storage, launch routing, and listener orchestration remain unintegrated. The encrypted TCP adapter is a tested library boundary and is not yet launched by the supervisor or worker. `MoonlightLaunchCrypto` validates the 16-byte hexadecimal `rikey`, clears temporary key buffers, and creates only the RTSP cipher selected by launch negotiation and video cipher selected by the parsed SDP encryption flag; the authenticated HTTP launch route that supplies those flags is still absent. UDP ping/control association and real Moonlight interoperability remain open. `MoonlightVideoPacketizer` generates bounded Reed-Solomon parity shards over each full plaintext datagram block, fills Moonlight shard metadata, then encrypts every data and parity shard when supplied a cipher. FEC percentage and minimum parity are configurable; validated session profiles can impose minimum parity and require an established cipher, causing plaintext packetization to fail closed. Frames requiring more than four blocks or unsupported multi-block negotiation are rejected. The layout is based on the inspected host flow but still needs differential golden vectors before the parity bytes can be considered compatible. `MoonlightUdpSender` transmits datagrams to a caller-provided peer; its session-bound constructor takes the accepted RTSP peer IP and negotiated client RTP/RTCP pair, applies the negotiated video-encryption bit and minimum FEC count, reserves the server RTP/RTCP pair before advertising it, and refuses to start without a cipher when video encryption was negotiated. The AES-GCM video primitive still requires a key established by a complete authenticated session. UDP send success means only that the local socket accepted a datagram. No media passes over supervisor control IPC, and the existing Syzygy-backed stream remains unchanged.

`SoftwareVideoPipeline` now joins a `FrameSource`, FFmpeg encoder, Moonlight packetizer, timestamp conversion, and UDP sender. It buffers the first access unit until an AUD boundary arrives, reports measured frame-receipt-to-send age in the short header, exposes local pipeline health counters, and flushes the final unit on shutdown. It is not launched by the supervisor and still requires caller-supplied authenticated session details, UDP peer, and negotiated capabilities. Capture currently copies each BGRA frame through a process pipe, and software encoding copies it again into FFmpeg. There is no DMA-BUF import, hardware encoder backend, audio or input path, configurable capture queue policy, or measured end-to-end latency. The current two-buffer GStreamer queue drops the oldest queued frame when its raw output pipe backpressures.

## Verification

GitHub Actions installs FFmpeg, builds/tests the workspace, checks complete and truncated capture-pipe frames, exercises an actual two-frame `libx264` encode/final flush, then checks encoded frames traveling through Moonlight packetization to a local UDP receiver, and asserts measured pipeline-local health counters. Unit coverage also checks RTP headers, marker placement, sequence rollover, FU-A reassembly, malformed NAL inputs, UDP delivery to local test sockets, bounded incremental RTSP parsing, fragmented ANNOUNCE over a TCP connection, ordered RTSP replies through PLAY/TEARDOWN, clean control disconnect and mid-request disconnect, encrypted ANNOUNCE request/response transport and idempotent retransmission with one lifecycle event, RTSP state ordering/replay, SDP profile extraction and rejection, server/client UDP port negotiation, actual paired RTP/RTCP reservation, capture limits, bounded two-frame capture queue configuration, Annex-B access-unit boundaries, Moonlight data/parity shard metadata and sequence/block boundaries, Reed-Solomon recovery, profile-driven encryption requirements, AES-GCM known-answer output, nonce uniqueness, authentication failure on tampering, and PIN-derived-key known-answer/validation vectors, plus AES-128-ECB known-answer, block-boundary, round-trip, and size-limit vectors, plus launch-key hexadecimal/length rejection and per-launch cipher construction, plus four-stage pairing query/XML routing and bounded malformed-query rejection, plus pending identity/salt/certificate validation and approval-expiration behavior, coordinator request deduplication/PIN binding/preflight behavior, fragmented HTTP parsing and query decoding, plus atomic server-identity/client-record round trips, client revocation, malformed record rejection, Linux private-mode assertions, restricted construction of authorized client records, profile-driven encryption-bit separation, session-bound UDP peer/port selection, and fail-closed missing-cipher setup. Pairing transaction tests complete the four cryptographic stages with test-only RSA identities, replay an exact final request idempotently, reject conflicting retries, reject out-of-order requests, and reject malformed challenges and client proofs. These tests establish code-level boundaries only; they do not establish portal operation, complete Moonlight parity compatibility, pairing endpoint integration or persistent authorization, or client interoperability.

## Next extraction work

1. Complete HTTPS request parsing/listener integration, connect operator approval to pending requests, persist only verified pairing results through the new store, and implement the TLS pairing confirmation stage. Then attach RTSP to an isolated worker with bounded listeners and finite socket timeouts.
2. Add differential golden vectors against the pinned Moonlight/Syzygy behavior for data/parity block contents, shard metadata, and encrypted parity packets; parity generation is now integrated but not yet client-validated.
3. Connect portal session acquisition and capture lifecycle to the worker; validate PipeWire/GStreamer format negotiation and robust cancellation.
4. Integrate capture, encoding, Moonlight packetization, and UDP with a bounded stale-frame policy; then add capability-gated hardware encoders and explicit DMA-BUF ownership where supported.
5. Wire authenticated session, encoded frames, Moonlight packetization, FEC, encryption, pacing, UDP, and measured lifecycle/health as a single isolated Rust path; preserve the Syzygy fallback until real Moonlight and hardware comparisons pass.

The current prototype must not be used as a Moonlight host. The next usable milestone requires real encoded input, the protocol compatibility layer, and a real-client verification run.
